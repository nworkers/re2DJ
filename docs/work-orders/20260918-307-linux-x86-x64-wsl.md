순서는 L0→L1→L2→L3→L4→L5→L6→L7이다. L3에서 확인한 callback/thread 또는 보호 계층 의존성은 필요한 후속 작업의 최소 부분을 앞당긴다. 단계를 통과할 때마다 x86·x64를 함께 검증하며 한쪽만 성공한 상태로 지원 완료를 선언하지 않는다.

*Sequence: L0 through L7. Dependencies discovered during L3 may pull forward the minimum required callback/thread or protection-boundary work. Validate both architectures at every gate; success on one does not establish dual-architecture support.*

*Record each candidate's pinned revision, file licenses, transitive dependencies, size, call overhead, and test results in its work log. Integrate suitable candidates behind adapters; otherwise record the reason and minimum custom implementation scope. Use asset-free fixtures. Library adoption does not establish Win32 semantics or original-game execution correctness.*

## 검증 운영 / Validation workflow

1. 소스는 현재 checkout을 기준으로 하되 WSL build 산출물은 Linux filesystem의 별도 x86/x64/helper 디렉터리에 둔다. git 작업 주체를 하나로 유지하고 Windows build tree를 재사용하지 않는다.
2. L0에서 기존 `scripts/test_linux_native_helper_probe.sh` 내용을 기준으로 build 경로를 지정해 검증한다. 현재 스크립트는 저장소 아래 build를 사용하므로 외부 build 지원은 후속 변경이다. 패키지 이름·가용 아키텍처·라이선스를 확인한 뒤 필요한 의존성만 준비한다.
3. L1부터 CI에 x86/x64 × GCC/Clang의 build·unit tests와 i386 helper 통합 검증을 넣는다. 원본 자산 없는 합성 테스트를 필수로 하고 WSLg GUI/audio 및 실제 게임 검증은 별도 기록한다.
4. 각 runtime 결과에 commit·host ELF 폭·helper ELF 폭·kernel·compiler·target/hash·옵션·stop reason을 기록한다. HDD/덤프는 저장소에 추가하지 않고 사용자 지정 원본과 별도 overlay만 사용한다.
5. 최종 32비트 Linux 검증 환경이 확보되지 않으면 WSL i386 사용자 공간 통과와 native x86 미확인을 따로 기록한다. 일반 Linux x64에서도 화면·소리·입력 회귀를 확인한다.

*Use the current source checkout with separate x86/x64/helper build trees on the Linux filesystem and one Git owner. Base L0 on the existing helper test script, adapting commands to external build paths; external-directory script support is future work. Confirm dependency availability, architectures, and licenses before installation. From L1, add x86/x64 × GCC/Clang build/unit and helper integration CI without original assets; record GUI/audio/game checks separately. Runtime evidence includes commit, ELF classes, kernel, compiler, target/hash, options, and stop reason. Keep HDD/dumps outside the repository and writes in a separate overlay. Record native x86 as unverified until an actual 32-bit Linux environment is available, and also test ordinary Linux x64 multimedia behavior.*

## 위험과 첫 착수점 / Risks and first implementation task

주요 위험은 Windows가 암묵적으로 제공하던 loader·SEH·TLS·message 의미, i386 SDL/GL/audio 의존성, callback 중첩 시 IPC 교착, 32비트 주소 공간·큰 파일 처리, frame/PCM 전송량이다. 기능 확인 전 shared-memory 최적화나 별도 x86 전용 실행기를 추가하지 않는다. 미지원 CPU/ABI 상태는 진단하고 멈추며 signal 보고 성공을 SEH 구현 완료로 취급하지 않는다.

*Main risks are loader/SEH/TLS/message semantics previously supplied by Windows, i386 multimedia dependencies, nested-callback deadlocks, 32-bit address-space/large-file handling, and frame/PCM transport volume. Do not add shared-memory optimization or a second x86 execution path before correctness is established. Diagnose unsupported CPU/ABI state; signal reporting is not guest SEH support.*

다음 실제 작업은 **L0 기준선 재현**이다. 설치된 WSL의 환경을 조사하고 기존 synthetic 검증을 현재 commit에서 재현한 뒤, 결과를 근거로 L1의 구체적인 파일 변경 목록을 작성한다. 공식 target 및 HDD·overlay 경로는 실제 게임 검증 시작 전에 사용자 제공 경로로 확정한다.

*The next implementation task is L0 baseline reproduction: inventory the installed WSL environment, reproduce existing synthetic checks at the current commit, and use that evidence to specify L1 file changes. Select an official target and user-provided HDD/overlay paths before game validation begins.*
