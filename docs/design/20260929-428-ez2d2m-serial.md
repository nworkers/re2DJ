# 작업 428 설계 — ez2d2m이 열지 못한 COM1 핸들 / Task 428 design — the COM1 handle ez2d2m fails to open

선행: [작업 427 설계](20260929-427-ez2d2m-linux.md)

## 배경 / Background

Linux에서 ez2d2m에 코인을 넣으면 `kernel32 WriteFile(0xFFFFFFFF, …, lpOverlapped)`에서 멈췄다(사용자 로그, 117,705번째 호출, 반환 주소 `0x0040C288`). 원본을 분석한 흐름은 다음과 같다.

- **보드 시작**(`0x40B209`): 시리얼 클래스(`this + 0x1474`)의 열기 함수(`0x40C050`)가 `CreateFileA("COM1", GENERIC_READ|GENERIC_WRITE, 0, NULL, OPEN_EXISTING, FILE_FLAG_OVERLAPPED|FILE_ATTRIBUTE_NORMAL, NULL)`을 부른다. 이것이 실패하면 핸들 `-1`을 멤버에 남긴 채 0을 돌려주는데, 호출자는 결과를 보지 않는다. 설정 호출(`SetCommMask`, `SetupComm`, `PurgeComm`, `SetCommTimeouts`, `GetCommState`, `SetCommState`)과 읽기 스레드 생성은 성공했을 때만 한다.
- **코인 처리**(`0x41CDE0` 등): 크레딧 카운터(`0x7FE340`)를 올린 뒤 쓰기 함수(`0x40C260`)로 4바이트를 보낸다. 쓰기 함수는 `WriteFile(h, buf, n, &count, &this->overlapped)`를 부른다. 실패하고 `GetLastError`가 `ERROR_IO_PENDING`이 아니면 `ClearCommError(h, &errors, &stat)`를 부르고 0을 돌려준다.
- **닫기 함수**(`0x40C230`): `SetCommMask(h, 0)`, `PurgeComm(h, 0xF)`, `CloseHandle(h)` 순서로 부른다.

*Inserting a coin into ez2d2m on Linux stopped at `kernel32 WriteFile(0xFFFFFFFF, …, lpOverlapped)` (the user's log, call 117,705, returning to `0x0040C288`). The original's flow is as follows.*
- ***Board start** (`0x40B209`): the serial class's open (`0x40C050`, at `this + 0x1474`) calls `CreateFileA("COM1", GENERIC_READ|GENERIC_WRITE, 0, NULL, OPEN_EXISTING, FILE_FLAG_OVERLAPPED|FILE_ATTRIBUTE_NORMAL, NULL)`. If that fails, it returns 0 and leaves handle `-1` in its member, and the caller ignores the result. The setup calls (`SetCommMask`, `SetupComm`, `PurgeComm`, `SetCommTimeouts`, `GetCommState`, `SetCommState`) and the reader thread happen only on success.*
- ***A coin** (`0x41CDE0` and others): after raising the credit counter (`0x7FE340`), the game sends four bytes through the write function (`0x40C260`). That calls `WriteFile(h, buf, n, &count, &this->overlapped)`, and when it fails with anything but `ERROR_IO_PENDING`, calls `ClearCommError(h, &errors, &stat)` and returns 0.*
- ***The close function** (`0x40C230`) calls `SetCommMask(h, 0)`, `PurgeComm(h, 0xF)`, and `CloseHandle(h)`.*

COM 포트가 없는 Windows 11 PC에서는 `COM1` 열기가 Linux와 같이 `ERROR_FILE_NOT_FOUND`로 실패하고, 게임은 그대로 진행한다.

*On a Windows 11 PC without a COM port, opening `COM1` fails with `ERROR_FILE_NOT_FOUND` as on Linux, and the game carries on.*

## Windows 11 측정 / Windows 11 measurements

`scratchpad/comm428`에서 측정했다. 핸들은 `INVALID_HANDLE_VALUE`와 아무것도 가리키지 않는 `0x1234` 두 가지이고, 결과는 같았다(`CloseHandle`만 다르다).

| 호출 / Call | 결과 / Result |
| --- | --- |
| `CreateFileA("COM1", …)` | `INVALID_HANDLE_VALUE`, 오류 2 |
| overlapped `WriteFile`·`ReadFile` | FALSE, 오류 6(`ERROR_INVALID_HANDLE`), 전송 수 0, `OVERLAPPED.Internal` = `0x103`(`STATUS_PENDING`) |
| 일반 `WriteFile` | FALSE, 오류 6, 전송 수 0 |
| `SetCommState`, `GetCommState`, `SetCommTimeouts`, `PurgeComm`, `SetupComm`, `SetCommMask`, `ClearCommError`, overlapped `WaitCommEvent` | FALSE, 오류 6, 출력 인자는 그대로 |
| `GetOverlappedResult(h, pending, &n, FALSE)` | FALSE, 오류 996(`ERROR_IO_INCOMPLETE`), `n`은 그대로 |
| `CloseHandle(INVALID_HANDLE_VALUE)` | TRUE(현재 프로세스 pseudo-handle), 오류는 그대로 |
| `CloseHandle(0x1234)` | FALSE, 오류 6 |

*Measured in `scratchpad/comm428` with two handles, `INVALID_HANDLE_VALUE` and a `0x1234` that names nothing; they gave the same results except for `CloseHandle`:*
- *`CreateFileA("COM1", …)`: `INVALID_HANDLE_VALUE` with error 2.*
- *Overlapped `WriteFile` and `ReadFile`: FALSE with error 6 (`ERROR_INVALID_HANDLE`), a transfer count of 0, and `OVERLAPPED.Internal` set to `0x103` (`STATUS_PENDING`).*
- *Plain `WriteFile`: FALSE with error 6 and a count of 0.*
- *The eight serial functions (`SetCommState`, `GetCommState`, `SetCommTimeouts`, `PurgeComm`, `SetupComm`, `SetCommMask`, `ClearCommError`, and overlapped `WaitCommEvent`): FALSE with error 6, outputs untouched.*
- *`GetOverlappedResult(h, pending, &n, FALSE)`: FALSE with error 996 (`ERROR_IO_INCOMPLETE`), `n` untouched.*
- *`CloseHandle(INVALID_HANDLE_VALUE)`: TRUE (the current process's pseudo-handle), the error left alone.*
- *`CloseHandle(0x1234)`: FALSE with error 6.*

## 결정 / Decisions

1. **판정 helper `NamesNoGuestObject`**: 열린 guest 파일, 장치, 이벤트, 스레드, 프로세스 핸들 중 어느 것도 아니면 "아무것도 가리키지 않는" 핸들로 본다. `INVALID_HANDLE_VALUE`도 여기에 든다. 현재 프로세스 pseudo-handle이기도 하지만, 파일·시리얼 함수는 측정대로 이것을 무효 핸들로 다룬다.
   *The `NamesNoGuestObject` helper: a handle that is no open guest file, device, event, thread, or process handle names nothing. `INVALID_HANDLE_VALUE` counts as nothing: although it is also the current process's pseudo-handle, the file and serial functions treat it as invalid, as measured.*
2. **overlapped 읽기·쓰기**: 그런 핸들이면 측정값대로 실패한다. 열린 파일에 대한 overlapped 전송은 여전히 모델하지 않는다.
   *Overlapped transfers fail as measured on such a handle. Overlapped transfers on an open file stay unmodelled.*
3. **시리얼 함수 8개**: resolve-only에서 구현 export로 바꾼다. 그런 핸들이면 FALSE와 오류 6을 돌려준다. 열린 핸들이면 멈춘다. COM 포트는 열리지 않으므로 guest가 이 함수들에 유효한 시리얼 핸들을 넘기는 일은 없다.
   *The eight serial functions move from resolve-only to implemented exports: FALSE with error 6 on such a handle, and a stop on an open one. No COM port opens, so a guest never hands them a working serial handle.*
4. **`GetOverlappedResult`**: pending 상태이고 기다리지 않는 경우만 측정대로 `ERROR_IO_INCOMPLETE`를 돌려준다. 기다리는 호출이나 완료된 작업은 멈춘다. 여기서는 비동기로 끝나는 전송이 없다.
   *`GetOverlappedResult` returns `ERROR_IO_INCOMPLETE` only for a pending operation asked about without waiting, as measured. Waiting, or a finished operation, stops; nothing here completes asynchronously.*
5. **`CloseHandle(INVALID_HANDLE_VALUE)`**: 측정대로 TRUE를 돌려준다.
   *`CloseHandle(INVALID_HANDLE_VALUE)` returns TRUE, as measured.*

Windows 제품은 실제 kernel32를 쓰므로 바뀌는 것이 없다.

*The Windows product uses the real kernel32, so nothing changes there.*

## 정정 / Correction

작업 427은 "코인을 넣어도 두 host 모두 크레딧이 오르지 않는다"고 기록했다. 이번에 Windows `keybd_event`로 F5를 창에 전달하자 Linux x64, Linux x86, Windows 모두 크레딧이 올랐다. 그래서 공용 보드의 코인 매핑(`0x304` bit 0)은 동작한다. 작업 427의 문서와 TODO를 고쳤다.

*Task 427 recorded that a coin raised the credit count on neither host. This time F5 was delivered to the window with Windows `keybd_event`, and the count rose on Linux x64, Linux x86, and Windows, so the shared board's coin mapping (`0x304` bit 0) works. Task 427's documents and the TODO were corrected.*
