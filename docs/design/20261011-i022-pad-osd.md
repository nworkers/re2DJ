# #22 설계: 게임패드로 OSD 열기와 조작 (LT+RT+Y)

이슈: [#22](https://github.com/reexec/re2DJ/issues/22) · 참고: rePIU v0.0.217(#55, `docs/design/20261010-i055-pad-osd.md`) · 관련: [#20 종료 조합](20261010-i020-pad-quit-combination.md), 작업 444(게임패드 입력)

## 배경

re2DJ의 OSD(`ui/osd`)는 백틱 키로 열고 마우스로만 조작합니다. 키보드·마우스 없는 스팀덱 게임 모드에서는 쓸 수 없습니다. OSD는 ImGui의 플랫폼 backend를 쓰지 않고 `SdlHostPresentation`이 넣어 주는 입력(마우스 위치·버튼)만 받습니다.

## 결정 (사용자: rePIU #55와 같게)

* **열고 닫기**: 한 패드에서 LT + RT + Y(North)를 **누르는 순간** OSD를 토글합니다. 유지 시간은 없습니다. 종료 조합(LT+RT+L3+R3)과 Y·스틱 클릭이 달라 겹치지 않습니다. 백틱도 그대로 됩니다.
* **열려 있는 동안**: 패드는 OSD 탐색에 쓰이고 게임에는 가지 않습니다. D-pad(와 왼쪽 스틱)로 항목을 옮기고 A로 고르며, B는 열린 메뉴(콤보)를 닫고, 직전 프레임에 열린 메뉴가 없으면 OSD를 닫습니다. 열릴 때 OSD 창에 포커스를 줍니다.
* **닫힌 뒤**: 닫는 순간 누르고 있던 패드 입력(닫은 B, 조합의 LT·RT·Y)은 그 버튼을 뗄 때까지 게임에 숨깁니다. 그래서 OSD를 닫는 동작이 게임 입력이 되지 않습니다.
* **키보드·마우스**: 지금과 같습니다. 키보드는 OSD가 열려 있어도 게임으로 가고, 마우스 버튼은 OSD가 가집니다.

## re2DJ에서 다른 점

rePIU의 기본 배치에서는 LT·RT·Y가 비어 있지만, re2DJ EZ2DJ 기본 배치(#14)에서는 LT·RT가 이펙터 3·4이고 Y가 1P 4번 키입니다. 그래서 조합을 이루는 버튼을 하나씩 누르는 동안, 즉 OSD가 열리기 전까지는 게임에도 들어갑니다. 열린 뒤에는 관문이 막고, 닫힐 때 누르고 있던 버튼은 뗄 때까지 숨기므로 닫는 쪽에서는 게임에 들어가지 않습니다. 이 동작은 같은 버튼을 쓰는 종료 조합(#20)과 같습니다.

## 구조

* **입력 계층(`re2dj/input/pad_osd_chord.h`, 헤더만·SDL 없음)**: `IsPadOsdChordDown`(한 패드 / 패드 목록; 여러 패드에 나눈 것은 아님), `PadChordEdge`(눌리는 순간 한 번 참), `PadGameGate`(막힘 중 게임에 빈 상태, 막힘이 풀릴 때 눌려 있던 입력은 뗄 때까지 숨김). `GamepadControls` 단위입니다.
* **OSD(`ui/osd`)**: `SetGamepad(GamepadControls)`로 합친 패드 상태를 받아, 바뀐 입력을 ImGui 게임패드 키(`GamepadDpad*`, `GamepadFace*`, `GamepadL/R1`, `GamepadLStick*`)로 넘깁니다. `NavEnableGamepad`와 `HasGamepad`를 켜고, 열릴 때 창에 포커스를 줍니다. B 처리와 닫기는 OSD 안에서 합니다.
* **호스트(`SdlHostPresentation::Present`)**: 패드를 읽은 뒤 (1) OSD 조합의 가장자리면 OSD를 토글하고, (2) 관문을 OSD가 보이는지에 맞춰 게임에 줄 상태를 거르고, (3) OSD가 보이면 합친 상태를 OSD에 넘깁니다. 종료 조합(#20)은 관문 앞의 원래 패드 상태로 봅니다.

## 검증

* 단위 테스트: OSD 조합(한 패드 / 나눔 / 빠짐), 가장자리(한 번만, 떼고 다시), 관문(막힘 중 빈 상태, 풀릴 때 눌린 입력 숨김, 뗀 뒤 다시 누르면 보임).
* 실제 패드(Linux): 게임 중 LT+RT+Y로 열기, D-pad·A로 항목 바꾸기(셰이더 등), B로 메뉴 닫기와 OSD 닫기, 닫은 B가 게임에 가지 않음, 다시 LT+RT+Y로 열고 닫기.

# #22 Design: opening and driving the OSD with a gamepad (LT+RT+Y)

Issue: [#22](https://github.com/reexec/re2DJ/issues/22) · Reference: rePIU v0.0.217 (#55, `docs/design/20261010-i055-pad-osd.md`) · Related: [#20 exit chord](20261010-i020-pad-quit-combination.md), task 444 (gamepad input)

## Background

re2DJ's OSD (`ui/osd`) opens with the backtick key and is driven only by the mouse, so it is out of reach in Steam Deck game mode, which has neither keyboard nor mouse. The OSD uses no ImGui platform backend and takes only the input `SdlHostPresentation` hands it (mouse position and buttons).

## Decisions (the user: as rePIU #55)

* **Toggling**: LT + RT + Y (North) on one pad toggles the OSD **the moment** they are all down, with no hold time; it shares neither Y nor the stick clicks with the exit chord (LT+RT+L3+R3). Backtick still works.
* **While open**: the pad drives the OSD and none of it reaches the game: the d-pad (and the left stick) moves between items and A chooses; B closes an open menu (combo), or the OSD when no menu was open the frame before. The OSD window takes focus as it opens.
* **After closing**: pad input held as it closes (the B that closed it, the chord's LT, RT and Y) stays hidden from the game until that button is released, so closing the OSD never becomes game input.
* **Keyboard and mouse**: unchanged; the keyboard still reaches the game with the OSD open, and the mouse buttons belong to the OSD.

## Where re2DJ differs

rePIU leaves LT, RT and Y unbound by default, but re2DJ's EZ2DJ default (#14) makes LT and RT effectors 3 and 4 and Y player 1's key 4. So while the chord's buttons are being pressed one by one, before the OSD opens, they reach the game too; once it is open the gate blocks them, and a button held as it closes stays hidden until released, so the closing side never reaches the game. The exit chord (#20) behaves the same with its shared buttons.

## Structure

* **Input layer (`re2dj/input/pad_osd_chord.h`, header-only, no SDL)**: `IsPadOsdChordDown` (one pad, or a list of pads; not split across pads), `PadChordEdge` (true once as the chord goes down), and `PadGameGate` (nothing for the game while closed off, and input held as it reopens hidden until released), all in `GamepadControls`.
* **OSD (`ui/osd`)**: `SetGamepad(GamepadControls)` takes the merged pad state and passes changed controls on as ImGui gamepad keys (`GamepadDpad*`, `GamepadFace*`, `GamepadL/R1`, `GamepadLStick*`), with `NavEnableGamepad` and `HasGamepad` on and the window focused as it opens; B and closing are handled inside the OSD.
* **Host (`SdlHostPresentation::Present`)**: after reading the pads it (1) toggles the OSD on the chord's rising edge, (2) filters the game's state through the gate, closed off while the OSD shows, and (3) hands the merged state to the OSD while it shows. The exit chord (#20) still reads the raw pad state ahead of the gate.

## Verification

* Unit tests: the OSD chord (one pad, split, one missing), the edge (once, again after a release) and the gate (empty while closed off, held input hidden as it reopens, shown again after a release and a new press).
* Real pad (Linux): in game, open with LT+RT+Y, change items with the d-pad and A (a shader, say), close a menu and then the OSD with B, see the closing B never reach the game, and open and close again with LT+RT+Y.
