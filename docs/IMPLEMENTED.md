- **작업 294 — 보호 빌드 덤프로 legacy I/O helper RVA를 전부 대조했습니다.** 여섯 보호 빌드를 `--image-dump`로 실행해 `resumed` 덤프에 `re2dj_port_helper_scan`을 돌렸고, 바이트 폭 다섯 빌드(`ez2dj1st`·`ez2dj1stse`·`ez2dj3rd`·`ez2dj4th`·`ez2dj5th`)의 `inportb`/`outportb`가 **프로파일 값과 모두 정확히 일치**합니다. `entry` 덤프는 여섯 빌드 모두 0건이라 진입점이 복호화 이전이라는 결론이 전 빌드로 확인됐습니다. 작업 293의 전제(1st SE·5th 미확인, `0xc0000096` 정지)는 과거 기록이었고 두 빌드는 현재 크래시 없이 프레임을 그립니다. `ez2d2m`은 port I/O가 게임 코드에 인라인되어 시그니처 대상이 아니며 입력 지점 후보 두 곳을 추정으로 남겼습니다. 코드 변경은 낡은 프로파일 설명 문자열 두 곳뿐입니다. 근거: [작업 지시](work-orders/20260917-294-port-helper-dump-crosscheck.md), [작업 로그](work-logs/20260917-294-port-helper-dump-crosscheck.md), [분석](analysis/ez2dj-io-map.md).

  *Task 294 — cross-checked every legacy-I/O helper RVA against protected-build dumps. Six protected builds were run with `--image-dump` and `re2dj_port_helper_scan` run over each `resumed` dump; for the five byte-width builds (`ez2dj1st`, `ez2dj1stse`, `ez2dj3rd`, `ez2dj4th`, `ez2dj5th`) `inportb` and `outportb` **match the profile values exactly**. Every `entry` dump yields zero, confirming across all builds that the entry point precedes decryption. Task 293's premise that 1st SE and 5th were unconfirmed and stop at `0xc0000096` was historical, and both builds now draw frames without crashing. `ez2d2m` inlines its port I/O into game code and is outside the signature method; two input-site candidates are recorded as inferred. The only code change is two stale profile note strings. Evidence: [work order](work-orders/20260917-294-port-helper-dump-crosscheck.md), [work log](work-logs/20260917-294-port-helper-dump-crosscheck.md), [analysis](analysis/ez2dj-io-map.md).*

- **작업 293 — legacy I/O helper를 시그니처로 찾을 수 있게 했습니다.** 프로파일이 저장하는 `legacy_io_in_rva`·`legacy_io_out_rva`가 틀리면 privileged fault가 처리되지 않아 실행이 `0xc0000096`에서 멈추는데, 지금까지 이 값을 얻는 방법은 실행해서 fault 주소를 읽는 것뿐이었습니다. 1st SE 정식 빌드의 평문 `.text`를 읽어 두 helper가 고립된 함수가 아니라 컴파일러 런타임 `inp`/`outp` 계열이 폭별로 연속 배치된 **한 묶음**임을 확인했고, 다섯 형태의 바이트 시그니처를 확정했습니다. `re2dj::exe::ScanPortHelpers`와 오프라인 도구 `re2dj_port_helper_scan`이 이 시그니처로 helper를 찾습니다. 시그니처만으로 탐색했는데 `0x00038987`과 `0x000389ab`, 곧 `ez2dj1stse` 프로파일 값과 **정확히 일치**하는 주소가 나왔습니다. `.protect` 보호 빌드(3rd·4th·`ez2d2m`)의 디스크 파일에서는 0건이며, 이는 `.text`가 암호문이라는 뜻으로 작업 292와 일치합니다. 정리 과정에서 **`ez2dj1stse`와 `ez2dj5th`의 값이 그 빌드에서 확인된 것이 아님**이 드러났고, 두 빌드가 transform loop를 넘긴 뒤 정확히 `0xc0000096`에서 멈춘다는 기존 기록과 겹치면 Hardlock 응답이 아니라 I/O 경계가 원인일 수 있다는 **추정**이 섭니다. 확인은 각 빌드의 `resumed` 덤프 대조로 하며 실행이 필요합니다. 프로파일 값은 이번 작업에서 바꾸지 않았습니다. 근거: [설계](design/20260916-293-port-helper-signature-scan.md), [작업 지시](work-orders/20260916-293-port-helper-signature-scan.md), [작업 로그](work-logs/20260916-293-port-helper-signature-scan.md), [분석](analysis/ez2dj-io-map.md).

  *Task 293 — made the legacy I/O helpers findable by signature. A wrong `legacy_io_in_rva` or `legacy_io_out_rva` leaves the privileged fault unhandled and stops execution at `0xc0000096`, and until now the only way to obtain either was to run the build and read the faulting address. Reading the plaintext `.text` of the 1st SE canonical build showed the two helpers are not isolated functions but part of **one block** of the compiler runtime's `inp`/`outp` family laid out by width, and five byte signatures were established. `re2dj::exe::ScanPortHelpers` and the offline `re2dj_port_helper_scan` tool locate helpers from those signatures: searching from the signature alone returned `0x00038987` and `0x000389ab`, **exactly** the `ez2dj1stse` profile values. A `.protect` build's disk file yields zero hits for 3rd, 4th and `ez2d2m` alike, meaning `.text` is ciphertext, consistent with task 292. Laying out the confirmation status exposed that **the `ez2dj1stse` and `ez2dj5th` values were never confirmed against their own build**; together with the existing record that both stop at exactly `0xc0000096` past the transform loop, this makes it **inferred** that the I/O boundary, not the Hardlock response, may be the cause. Settling it needs each build's `resumed` dump and therefore a run. No profile value was changed. Evidence: [design](design/20260916-293-port-helper-signature-scan.md), [work order](work-orders/20260916-293-port-helper-signature-scan.md), [work log](work-logs/20260916-293-port-helper-signature-scan.md), and [analysis](analysis/ez2dj-io-map.md).*

- **작업 292 — 보호 빌드가 실행 중 복호화한 주 이미지를 뜰 수 있게 했습니다.** `.protect` 빌드는 디스크에 원본 코드가 없어 정적 분석이 불가능했습니다. 3rd 실행 파일 전체를 검색해도 그 게임이 자기 INI에 매번 쓰는 `TotalCoin`·`UseGameOver`조차 0건입니다. `--image-dump`가 진입점 복원 직후와 게스트 재개 후 두 시점에 주 이미지를 virtual 레이아웃 그대로 저장하므로 **파일 오프셋이 곧 RVA**이고, 귀속 sidecar가 어느 빌드의 어느 시점인지 증명합니다. 설계가 미확정으로 남긴 질문에도 답이 나왔습니다 — **진입점 breakpoint는 복호화 이전입니다.** 두 덤프가 6.8 MB 중 36.3%가 다르고, `entry`에는 0건인 INI 키 문자열이 `resumed`에는 2~4건씩 있습니다. 분석에는 `resumed`만 씁니다. PE 헤더가 디스크 파일과 일치하고 읽기 실패 범위가 없어 덤프 충실성도 확인했습니다. 부수적으로 `AutoPlay`가 EZ2DJ의 INI 키가 아님이 확정됐습니다. 근거: [설계](design/20260916-292-decrypted-image-dump.md), [작업 지시](work-orders/20260916-292-decrypted-image-dump.md), [작업 로그](work-logs/20260916-292-decrypted-image-dump.md), [분석](analysis/protected-build-runtime-decryption.md), [절차](guides/decrypted-image-dump.md).

  *Task 292 — made it possible to dump the main image a protected build decrypts at run time. A `.protect` build carries no original code on disk: searching the whole 3rd executable finds zero occurrences of even `TotalCoin` or `UseGameOver`, which that game writes into its own INI every run. `--image-dump` saves the main image at two points — just after the entry is restored and again once the guest has been running — in virtual layout, so **a file offset is the RVA**, with an attribution sidecar proving which build and which point. It also answered the design's open question: **the entry breakpoint is before decryption.** The two dumps differ across 36.3% of 6.8 MB, and INI key strings absent from `entry` appear two to four times in `resumed`, so only `resumed` is used for analysis. Dump fidelity was confirmed by the PE headers matching the disk file with no failed ranges. Incidentally, `AutoPlay` was established not to be an EZ2DJ INI key at all. Evidence: [design](design/20260916-292-decrypted-image-dump.md), [work order](work-orders/20260916-292-decrypted-image-dump.md), [work log](work-logs/20260916-292-decrypted-image-dump.md), [analysis](analysis/protected-build-runtime-decryption.md), and [procedure](guides/decrypted-image-dump.md).*

- **작업 291 — 3rd 프레임률이 SDL3의 타이머 해상도 요청에 얹혀 있음을 확정했습니다.** 3rd는 `timeBeginPeriod`를 한 번도 부르지 않는데(원본 파일 전체 검색 0건) NT 계열 기본 해상도 15.625 ms에서는 살아남을 수 없는 sleep 기반 리미터를 씁니다. 해상도를 올리는 것은 정적 링크된 **SDL3**이며, 서브시스템 하나만 초기화해도 `SDL_InitTicks`가 기본 힌트로 `timeBeginPeriod(1)`을 부릅니다. `SDL_TIMER_RESOLUTION=0`으로 그 요청만 제거하자 `Sleep` p50이 16.0 ms에서 27.5 ms로, 프레임률이 56.9 fps에서 **32.7 fps로 절반이 되었습니다.** 또한 게스트의 주기 계산이 고정 상수가 아니라 `목표 - 경과` 피드백임을 확정했습니다. 요청값과 직전 작업 시간의 상관이 -0.78~-0.98인데 둘의 **합은 16.94~17.35 ms로 일정**하며, 호스트 해상도를 바꿔도 움직이지 않습니다. 목표 주기는 60 Hz의 16.67 ms가 아니라 약 17 ms(58.8 Hz)로 추정되며 원본 상수 확인은 미확정입니다. `NtQueryTimerResolution`은 시스템 전역 값을 읽으므로 이 의존을 볼 수 없다는 점도 확인했습니다. 후속 측정에서 `timeGetTime`은 함께 뭉개지지 않음을 확인했으므로(같은 프로세스에서 시계 1 ms, `Sleep(15)` p50 25.87 ms), 요청을 잃었을 때 손상되는 것은 프레임률이고 게스트의 내부 시간 진행은 유지됩니다. 진단은 모두 `--guest-wait-trace`로만 켜집니다. 근거: [설계](design/20260915-291-timer-resolution-dependency.md), [작업 지시](work-orders/20260915-291-timer-resolution-dependency.md), [작업 로그](work-logs/20260915-291-timer-resolution-dependency.md), [분석](analysis/ez2dj3rd-frame-pacing.md), [배경](kb/windows-timer-resolution.md).

  *Task 291 — established that 3rd's frame rate rides on SDL3's timer-resolution request. 3rd never calls `timeBeginPeriod` (zero hits across the whole original file) yet uses a sleep-based limiter that cannot survive the NT family's 15.625 ms default. What raises the resolution is statically linked **SDL3**: initializing any subsystem takes `SDL_InitTicks` through its default hint into `timeBeginPeriod(1)`. Removing only that request with `SDL_TIMER_RESOLUTION=0` moved the `Sleep` p50 from 16.0 ms to 27.5 ms and **halved the frame rate from 56.9 fps to 32.7 fps.** The guest's period was also established as `target - elapsed` feedback rather than a fixed constant: the request correlates -0.78 to -0.98 with the preceding work while **their sum holds at 16.94-17.35 ms**, unmoved by changing the host resolution. That target is estimated at about 17 ms (58.8 Hz) rather than 60 Hz's 16.67 ms, with the original constant left unresolved. `NtQueryTimerResolution` was also shown unable to see this dependency, since it reads the system-wide value. A follow-up measurement confirmed `timeGetTime` does not degrade with it — a 1 ms clock beside a 25.87 ms `Sleep(15)` p50 in one process — so losing the request costs frame rate while the guest's internal advance of time holds. Every diagnostic is enabled only by `--guest-wait-trace`. Evidence: [design](design/20260915-291-timer-resolution-dependency.md), [work order](work-orders/20260915-291-timer-resolution-dependency.md), [work log](work-logs/20260915-291-timer-resolution-dependency.md), [analysis](analysis/ez2dj3rd-frame-pacing.md), and [background](kb/windows-timer-resolution.md).*

- **작업 290 — 게스트 대기 계정을 추가하고 3rd 프레임 예산을 전부 설명했습니다.** 주입 런타임의 `Sleep`·`WaitForSingleObject`·`timeGetTime` 래퍼가 소요 시간을 누적하고 facade가 프레임 창마다 한 줄로 보고합니다. 정적 IAT 패치만으로는 3rd의 호출에 닿지 않아(세 슬롯 모두 패치되었으나 계정 0건) 동적 `GetProcAddress` resolver에도 세 이름을 붙였고, 그 즉시 계정이 잡혔습니다. 3rd 타이틀 화면에서 프레임당 `Sleep` 1회에 16.8 ms(요청 16.3 ms), `Present` 0.26 ms, 나머지 약 0.7 ms로 17.8 ms 전부가 설명됩니다. 프레임 시간의 **94%가 게스트 자신의 `Sleep`** 이며, `WaitForSingleObject`는 프레임당 2회에 합계 0.12 ms로 무시할 수 있습니다. 제품 `--guest-wait-trace`로만 켜지며 옵션이 없으면 슬롯을 건드리지 않습니다. 근거: [설계](design/20260915-290-guest-wait-accounting.md), [작업 지시](work-orders/20260915-290-guest-wait-accounting.md), [작업 로그](work-logs/20260915-290-guest-wait-accounting.md).

  *Task 290 — added guest wait accounting and fully explained 3rd's frame budget. Injected-runtime wrappers around `Sleep`, `WaitForSingleObject` and `timeGetTime` accumulate their durations, and the facade reports one line per frame window. Static IAT patching alone did not reach 3rd's calls — all three slots patched, zero accounted — so the three names were added to the dynamic `GetProcAddress` resolver as well, which produced accounting immediately. On the 3rd title screen, one `Sleep` per frame at 16.8 ms (16.3 ms requested), a 0.26 ms present, and about 0.7 ms of remainder account for all 17.8 ms. **94% of frame time is the guest's own `Sleep`**, while `WaitForSingleObject` is called twice per frame for 0.12 ms total. It is enabled only by the product's `--guest-wait-trace`; without the option no slot is touched. Evidence: [design](design/20260915-290-guest-wait-accounting.md), [work order](work-orders/20260915-290-guest-wait-accounting.md), and [work log](work-logs/20260915-290-guest-wait-accounting.md).*
