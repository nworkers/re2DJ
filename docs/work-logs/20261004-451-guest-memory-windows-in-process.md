- **스킬 문서**: 도구 표, 7단계의 Windows·Linux 문단(Windows `--launch` 예 추가), 8단계 `write` 예시.

  *Environment: this PC had no Windows Python, Visual Studio, CMake or build; per the user's decision winget installed Python 3.12.10, CMake 4.4.3 and Visual Studio 2026 Build Tools 18.10 (the VCTools workload with recommended components). `roms/ez2dj4th` is empty, so no game files are present. Script: the Windows `tasklist` image-name lookup is gone; `ctypes` takes pids and parents from a Toolhelp32 snapshot, the command line from `NtQueryInformationProcess` class 60, the arguments from `CommandLineToArgvW` and the creation time from `GetProcessTimes`, matching under Linux's rule (a case-sensitive substring of an argument after the first, self and ancestors skipped, the `--launch` tree, the newest); `ancestors_of` takes Windows' parent map and cuts loops; on Windows `--launch` passes the command string unsplit and `taskkill /T /F` ends the tree; the docstring and the `--process` help describe both OSes. Skill document: the tool table, step 7's Windows and Linux paragraph with a Windows `--launch` example, step 8's `write` example.*

- **검증**
  - WSL `python3 -m py_compile`, `--help` 정상.
  - Windows 합성 대상(재실행 흉내: 같은 명령줄로 자신을 다시 띄우고, 같은 고정 주소 0x20000000에 처음 것은 1, 둘째는 2, 런처의 자식 쪽 둘째는 3을 둠. 스크래치 스크립트로만 썼고 저장소에 넣지 않음):
    - `read --process FAKE.EXE` → 2(둘째 선택), `write ... 7 --yes` → `2 -> 7`, 대상 쪽에서도 `2 -> 7`을 관찰.
    - `--process fake.exe` → 일치 없음(대소문자 구분 확인).
    - `poll --process CHILD.EXE --launch "<python> fake_relaunch.py ... --launcher"` → 프로세스 넷 중 런처 자식의 둘째(3)를 고름. 끝난 뒤 남은 대상 프로세스 0개.
  - WSL Linux 합성 대상(`MAP_FIXED`로 0x20000000에 5): `poll --launch` → 5, 끝난 뒤 남은 프로세스 없음. Linux 동작은 그대로다.
  - Windows x86 Debug build(새 환경에서 처음 configure, `scripts/build.ps1`): 성공. 경고는 SDL3·SDL3_mixer 헤더의 C4819(코드 페이지 949)뿐이다.
  - CTest: 4개 중 3개 통과. `re2dj_audio_stream_progress_test`는 이 PC의 **Smart App Control**(`VerifiedAndReputablePolicyState` = 1, 강제)이 서명 없는 실행 파일을 막아 시작되지 못했다("An Application Control policy has blocked this file"). 코드 문제가 아니며 작업 450의 다른 PC 검증에서는 통과했다. `re2dj.exe`는 같은 정책 아래 정상 실행된다.
  - **하지 못한 것**: 실제 `re2dj.exe` 게임 run에 대한 `read`. 이 PC에 게임 자산이 없어 게스트가 오래 살아 있는 run을 만들 수 없다. 재실행 구조와 런처 자식 구조는 합성 대상으로 확인했다. 자산이 있는 환경에서 `python guest_memory.py read --process ez2dj4th 0x00400000`(이미지 머리 `MZ`, 0x00905a4d 기대)로 확인할 수 있다.

  *Verification: WSL `py_compile` and `--help` pass. A Windows synthetic target imitating the relaunch (it starts itself again with the same command line and holds, at the same fixed address 0x20000000, 1 in the first, 2 in the second and 3 in a launcher child's second; a scratch script kept out of the repository): `read --process FAKE.EXE` gives 2, picking the second; `write ... 7 --yes` reports `2 -> 7`, which the target also saw; `--process fake.exe` matches nothing, matching being case-sensitive; `poll --process CHILD.EXE --launch ... --launcher` picks the launcher child's second (3) of four processes, none left afterwards. A WSL Linux synthetic target (5 at 0x20000000 through `MAP_FIXED`): `poll --launch` reads 5 and leaves nothing behind, so Linux behaves as before. The Windows x86 Debug build, configured for the first time in the new environment through `scripts/build.ps1`, succeeds with only C4819 (code page 949) warnings from the SDL3 and SDL3_mixer headers. CTest passes 3 of 4: `re2dj_audio_stream_progress_test` could not start because this PC's **Smart App Control** (`VerifiedAndReputablePolicyState` = 1, enforcing) blocked the unsigned executable ("An Application Control policy has blocked this file"), not a code fault, the test having passed in task 450 on another PC; `re2dj.exe` runs under the same policy. Not done: a `read` against a real `re2dj.exe` game run, as this PC has no game files to keep a guest alive; the relaunch and launcher-child structures were covered by the synthetic target, and with the files present `python guest_memory.py read --process ez2dj4th 0x00400000` should read the image's `MZ` header (0x00905a4d).*
