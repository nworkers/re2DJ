### 요구사항

작업 244 이후 `ez2d2m`이 `.protect`에서 `ExitProcess(0)`으로 종료하는 원인을 확인합니다.

코드는 바꾸지 않았습니다. 진단 중 임시 패치를 넣었다가 되돌렸으므로 순수 관측 작업입니다.

### 한 일

1. 요청 순서를 라운드 단위로 정리했습니다.
2. 종료 직전 요청의 descriptor header 필드를 확인했습니다.
3. 현재 HLE가 그 요청을 어떻게 처리하는지 코드에서 확인했습니다.
4. 임시 진단 빌드로 그 요청만 거부해 인과성을 시험했습니다.
5. 진단 패치를 되돌리고 복원을 확인했습니다.

### 결론 — 확인됨

**종료는 Hardlock Function `0x0001` descriptor 요청에서 결정됩니다.**

종료 직전 순서는 device 재개방 → handshake 2회 → Function `0x0000` descriptor → port `0x030a` 램프 순서열 8회 → **Function `0x0001` descriptor 2회** → `ExitProcess(0)`입니다. 두 번째 요청은 `data_address=0x001e0000`을 실어 보냅니다.

현재 `HardlockDevice`에는 Function `0x0001` 처리가 없습니다. descriptor 요청을 그대로 출력에 복사하고 status를 0으로 지울 뿐이며, `data_address`는 진단 출력용으로 파싱만 하고 사용하지 않습니다. 보호 계층은 "성공" status와 함께 자기 요청을 그대로 돌려받습니다.

### 인과성 시험

echo 응답이 종료의 원인인지, 아니면 종료가 다른 이유로 일어나고 이 요청이 우연히 그 앞에 오는지 구분해야 했습니다. 임시 진단 빌드에서 Function `0x0001` 요청만 거부하고 나머지는 그대로 두었습니다.

| | 정상 (echo) | 진단 (거부) |
| --- | --- | --- |
| trace 줄 | 256 | 270 |
| 요청 합계 | 31 | 35 |
| handshake | 4 | 6 |
| descriptor | 15 | 17 |
| rejected | 0 | 4 |

거부하면 보호 계층이 handshake를 다시 하고 `0x0001`을 재요청하기를 네 번 반복한 뒤 종료합니다. **재시도한다는 것은 이 응답을 실제로 검사한다는 뜻입니다.** echo를 주면 재시도 없이 즉시 종료하므로, echo는 형식은 통과하고 내용에서 거절됩니다.

이 시험이 "요청 순서상 앞에 있다"와 "원인이다"를 갈랐습니다. 순서만으로는 둘을 구분할 수 없었습니다.

### 6th와의 대조

[6th 분석](../analysis/ez2dj6th-hardlock.md)은 6th의 두 descriptor 요청이 Function `0x0000`과 `0x0001`이며 최종적으로 주 진입이 `-1`을 반환해 종료한다고 기록합니다. 두 제품이 같은 미구현 요청에서 멈춥니다. 따라서 이것은 `ez2d2m` 고유 문제가 아니라 이 저장소의 Hardlock 경계에 공통으로 빠져 있는 항목입니다.

### 미확정

- Function `0x0001`이 무엇을 요구하는지. `data_address`가 가리키는 버퍼에 동글 메모리를 쓰는 요청인지, 256바이트 descriptor 안에 응답을 담는 요청인지.
- 유효한 응답 내용. 이 저장소는 보호 응답을 추측해 만들지 않으므로, 이 값은 외부 도구나 실제 동글에서 와야 합니다.
- 첫 라운드의 `.protect` `0xc0000005`가 이 경계와 관련이 있는지.
- `candidate-70`의 정오와의 독립성. transform 11건이 모두 응답된 뒤 별도 단계에서 종료가 결정되므로 무관해 보이지만, 확정하려면 유효한 `0x0001` 응답이 필요합니다.

### Requirement

Determine why `ez2d2m` ends in `ExitProcess(0)` from `.protect` after task 244. No code changed; a temporary patch was used during diagnosis and reverted, so this is purely observation.

### Conclusion — confirmed

**The exit is decided at the Hardlock Function `0x0001` descriptor request.**

The sequence before it is: reopen the device, two handshakes, a Function `0x0000` descriptor, the eight-step lamp sequence on port `0x030a`, then **two Function `0x0001` descriptor requests**, then `ExitProcess(0)`. The second carries `data_address=0x001e0000`.

`HardlockDevice` has no handling for Function `0x0001`: it copies a descriptor request to the output and clears the status word, and `data_address` is parsed for the diagnostic line and used nowhere. The protection gets its own request back with a status meaning success.

### The causality test

Ordering alone cannot separate "this request precedes the exit" from "this request causes it", so a temporary diagnostic build refused Function `0x0001` requests alone. The normal build gives 256 lines and 31 requests with 4 handshakes, 15 descriptors and no rejections; refusing gives 270 lines and 35 requests with 6 handshakes, 17 descriptors and 4 rejections.

Refused, the protection handshakes again and re-requests `0x0001`, four times over, before exiting. **Retrying means it really does inspect the answer.** Echoed, it exits immediately without retrying, so the echo passes the shape check and is rejected on content.

### Contrast with 6th

[The 6th analysis](../analysis/ez2dj6th-hardlock.md) records that 6th's two descriptor requests are Function `0x0000` and `0x0001` and that its main entry ultimately returns `-1` and exits. Two products stop at the same unimplemented request, so this is not specific to `ez2d2m` but a gap in this repository's Hardlock boundary.

### Verification

The diagnostic patch is reverted — `git diff src/hle/hardlock/device.cpp` is empty — and the restored build reproduces 256 lines and 31 requests, matching the pre-diagnosis figures. The full Windows x86 Debug build passes with zero warnings and unit tests report 1550 checks with 0 failures. No code changed.

### Unresolved

What Function `0x0001` asks for — whether it writes dongle memory into the buffer at `data_address` or returns its answer inside the 256-byte descriptor. What a valid answer contains; this repository does not invent protection responses, so that value has to come from an external tool or a real dongle. Whether the round-one `.protect` `0xc0000005` relates to this boundary. And whether this is independent of `candidate-70` being correct: the exit is decided in a separate step after all eleven transforms were answered, which suggests it is, but settling that needs a valid `0x0001` answer.
