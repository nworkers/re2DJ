## 2026-10-05

- **준비**: `lscpu`·`glxinfo`로 이 Linux 기계가 작업 453의 Windows PC와 같은 CPU(Ryzen 5 5600X)·GPU(RTX 4090)임을 확인했다. 디스플레이만 다르다(5120x2880 59.99 Hz 두 대). 다섯 타깃 모두 x64에서 창을 열고 정상 종료하는 것을 10초 실행으로 확인했다. 규칙대로 현재 작업 브랜치(`release-notes-issue-refs`)에서 이어서 작업했다.
- **임시 측정 패치**(커밋하지 않음): `host_presentation.cpp`에 두 가지를 넣었다. `RE2DJ_BENCH_VSYNC_OFF`면 `config.present_sync = kImmediate`이고, `RE2DJ_BENCH_FPS_LOG`면 창 제목과 같은 `FrameRate` 값을 `BENCH fps` 로그로 남긴다. x64 4th vsync off에서 약 1,100 fps가 나와 vsync가 풀리는 것을 확인했다. 측정 뒤 `git checkout`으로 되돌려 x86·x64 Release를 다시 빌드했고, 두 바이너리에 `BENCH` 문자열이 없음을 확인했다.
- **측정**: scratchpad의 `bench.py`로 다섯 타깃 × vsync on/off × x64·x86 × 2회, 40회를 돌렸다(약 30분). x86은 `egl-wayland` v1을 지정했다. 1초마다 프로세스 트리의 utime+stime·`VmRSS`·`VmData`·`smaps_rollup` Private를 샘플링했다. vsync on에서 2 fps 미만이 있으면 다시 재도록 했는데, 다시 잰 실행은 없었다. 두 회의 평균 FPS 차이는 4th x86 6%, 5th x86 7%, 나머지 4% 이하였다.
- **대조 측정**: x86만 느리고 CPU가 100% 밑인 이유를 가르려고 `bench2.py`로 vsync off를 한 번씩 더 쟀다. x64 + `egl-wayland` v1(4th 703, 1st SE 1570, 6th 498 fps, CPU 66~79%), x64 X11(1037·3141·741), x86 X11(757·1591·622, CPU 100~102%). 표시 경로가 주된 원인임을 확인했다.
- **문서**: `docs/analysis/linux-windows-performance.md`(조건, 처리량·대조·vsync on·메모리 표, Mermaid 표시 경로, 확인됨·추정·미확정 해석), `docs/analysis/README.md` 색인, Windows 성능 문서의 링크, `docs/TODO.md`(x86 X11 격차와 상주 private 원인 확인), 가이드의 NVIDIA 절(X11이 vsync off 처리량 1.6~1.7배).

  *Preparation: `lscpu` and `glxinfo` confirmed this Linux machine has task 453's Windows PC's CPU (Ryzen 5 5600X) and GPU (RTX 4090), only the displays differing (two 5120x2880 59.99 Hz); 10-second runs confirmed all five targets open their windows and end cleanly on x64; work continued on the current task branch (`release-notes-issue-refs`) as the rules say. Temporary measuring patch (not committed): in `host_presentation.cpp`, `RE2DJ_BENCH_VSYNC_OFF` sets `config.present_sync = kImmediate`, and `RE2DJ_BENCH_FPS_LOG` logs the title's `FrameRate` value as `BENCH fps`; x64 4th with vsync off gave about 1,100 fps, confirming vsync was off; afterwards `git checkout` reverted it, both Release builds were rebuilt, and neither binary holds a `BENCH` string. Measurement: `bench.py` in the scratchpad ran five targets × vsync on/off × x64 and x86 × 2, 40 runs in about 30 minutes, x86 pinning `egl-wayland` v1, sampling the process tree's utime+stime, `VmRSS`, `VmData` and `smaps_rollup` Private every second, set to retry any vsync-on run with a second below 2 fps (none needed); the two runs' average FPS differed by 6% for 4th x86, 7% for 5th x86 and 4% or less elsewhere. Control: to see why only x86 was slow with CPU under 100%, `bench2.py` ran vsync off once more each — x64 with `egl-wayland` v1 (4th 703, 1st SE 1570, 6th 498 fps, CPU 66 to 79%), x64 on X11 (1037, 3141, 741) and x86 on X11 (757, 1591, 622, CPU 100 to 102%) — confirming the presentation path as the main cause. Documents: `docs/analysis/linux-windows-performance.md` (conditions, throughput, control, vsync-on and memory tables, a Mermaid presentation-path diagram, confirmed, inferred and unresolved interpretation), the `docs/analysis/README.md` index, a link from the Windows performance document, `docs/TODO.md` (the x86 X11 gap and the resident private memory), and the guide's NVIDIA section (X11 giving 1.6 to 1.7 times the vsync-off throughput).*

- **결과 요약**: vsync on에서는 세 빌드 모두 평균 59.4~60 fps다. CPU는 Linux x64 4.0~12.6%, x86 8.4~18.5%, Windows 9.1~16.9%다. vsync off 처리량은 Linux x64가 Windows in-process의 ×0.98~×3.37, x86(v1)이 ×0.54~×1.03이다. 메모리는 RSS가 Windows working set보다 7~45% 많고, `VmData`는 Windows private bytes와 −4~+2%로 비슷하다.

  *Results: with vsync on all three builds average 59.4 to 60 fps, with CPU at 4.0 to 12.6% on Linux x64, 8.4 to 18.5% on x86 and 9.1 to 16.9% on Windows; vsync-off throughput on Linux x64 is ×0.98 to ×3.37 of the Windows in-process runner and on x86 (v1) ×0.54 to ×1.03; RSS is 7 to 45% above the Windows working set, and `VmData` is within −4 to +2% of Windows private bytes.*

- **하지 못한 것**: Windows를 다시 재지 않았다(이 기계는 Linux로 부팅 중이다). 작업 453의 한 번 측정값을 그대로 썼다. 프로파일링은 TODO로 남겼다.
