# 작업 113 — ez2dj4th MAME CHD HDD 작업 로그

## 한국어

### 작업 요약

`ez2dj4th` built-in target profile을 추가하고, shortcut의 기본 입력 경로를 정확히 `roms/ez2dj4th`로 선언했습니다. 추출 디렉터리만 전제로 하던 기존 profile 입력과 구분하기 위해 `HddInputKind::kMameChd` 및 `default_hdd_image_relative_path`를 추가했습니다. 4th 실행 파일의 내부 경로와 fingerprint는 CHD filesystem mount 전까지 확인되지 않은 상태로 남겼습니다.

사용자 피드백에 따라 직접 CHD v5 parser와 codec을 유지하는 방향을 중단하고 `libchdr`를 구현 경계로 선택했습니다. libchdr와 LZMA, miniz, Zstandard, dr_flac dependency를 `third_party/libchdr/` 아래에 보존하고, 공용 `MameChdImage` adapter에는 파일 경로, metadata 보존, logical byte 범위, hunk 경계, sector 단위만 맡겼습니다. CHD map, parent image, codec 해제는 libchdr에 위임합니다.

CLI에서 아직 `HddRoot`가 추출 디렉터리를 입력으로 받는 경계는 유지됩니다. 따라서 `re2dj ez2dj4th`가 CHD를 디렉터리로 잘못 열려고 하지 않고, CHD filesystem mount가 아직 연결되지 않았다는 명시적 `not implemented` 오류를 반환합니다. `re2dj_chd_probe`는 실제 CHD를 읽는 비실행 검증 경로입니다.

### 실제 CHD 검증

저장소에 포함하지 않은 로컬 자산 `roms/ez2d2m/ez2d2m.chd`를 다음 probe로 열었습니다.

```text
re2dj_chd_probe roms/ez2d2m/ez2d2m.chd
```

관찰 결과:

* CHD version 5
* logical size 134754762240 bytes
* hunk 4096 bytes, unit 512 bytes, 32899112 hunks
* codecs `lzma,zlib,huff,flac`
* `GDDD` metadata `CYLS:16383,HEADS:255,SECS:63,BPS:512`
* LBA 0 decode 성공 및 boot-sector signature `55aa`
* hunk 끝 8 bytes에서 다음 hunk로 걸치는 16-byte logical read 성공

이 검증은 libchdr가 실제 compressed map과 다중 codec을 처리하고 adapter가 sector를 복사해 반환함을 확인합니다. `ez2dj4th` 원본 CHD는 제공되지 않았으므로 해당 경로의 실제 파일명·filesystem·PE 경로는 아직 확인하지 않았습니다.

### 검증 상태

* libchdr C sources, dependency sources, adapter, probe의 MSVC 수동 compile/link 성공
* 실제 CHD probe exit code 0 및 위 geometry/LBA 결과 확인
* asset-free unit test에 빈 경로, 존재하지 않는 경로, codec 이름 회귀 추가
* `git diff --check` 완료
* 전체 CMake configure/build와 CTest는 SDL3 FetchContent clone이 현재 네트워크 제한으로 실패하여 이 작업에서 실행하지 못함

원본 CHD, 실행 파일, HDD 내용은 Git 변경에 포함하지 않았습니다.

### 후속 미완료

1. CHD directory 안에서 FAT/exFAT 구조를 읽는 read-only filesystem layer
2. 그 layer를 `HddRoot`/VFS에 연결하고 case-insensitive guest path를 제공하는 mount
3. `ez2dj4th` CHD에서 실제 executable 경로·working directory·fingerprint 확인
4. profile shortcut과 `re2dj --run ez2dj4th`를 CHD mount 및 Windows/Linux execution backend에 연결
5. guest write를 CHD 원본이 아닌 overlay로 보내는 정책

## English

### Summary

The `ez2dj4th` built-in target profile now declares the exact shortcut input path `roms/ez2dj4th`. `HddInputKind::kMameChd` and `default_hdd_image_relative_path` distinguish it from extracted-directory profiles. The 4th executable path and fingerprint remain unresolved until a CHD filesystem mount can inspect the image.

Following the user's feedback, the direct CHD-v5 parser and codec implementation was discarded in favor of `libchdr`. libchdr and its LZMA, miniz, Zstandard, and dr_flac dependencies are preserved under `third_party/libchdr/`. The shared `MameChdImage` adapter owns only the path, metadata retention, logical-range checks, hunk-boundary copying, and sector reads; libchdr owns CHD maps, parent images, and codec decoding.

The CLI still accepts extracted directories through `HddRoot`. `re2dj ez2dj4th` therefore reports an explicit not-implemented CHD-mount error instead of treating the profile as a directory. `re2dj_chd_probe` is the non-executing real-CHD validation path.

### Real-CHD validation

The probe opened the local, uncommitted asset `roms/ez2d2m/ez2d2m.chd` and confirmed CHD v5, a 134754762240-byte logical image, 4096-byte hunks, 512-byte units, 32899112 hunks, `lzma,zlib,huff,flac` codecs, `GDDD` geometry metadata, and a decoded LBA 0 with boot signature `55aa`. This demonstrates that libchdr handles the compressed map and multiple codecs while the adapter returns a logical sector. No `ez2dj4th` original CHD was provided, so its file name, filesystem, and PE path remain unverified.

### Verification status

* Manual MSVC compile and link succeeded for all libchdr/dependency C sources, the adapter, and the probe.
* The real-CHD probe exited with code 0 and produced the geometry/LBA results above, including a 16-byte cross-hunk read.
* Asset-free unit coverage now includes empty-path, missing-path, and codec-name regressions.
* `git diff --check` is part of the final verification.
* Full CMake configure/build and CTest were not runnable because SDL3 FetchContent cloning is blocked by the current network restriction.

No original CHD, executable, or HDD contents were added to Git.

### Follow-up work

FAT/exFAT read-only filesystem support, the `HddRoot`/VFS mount, confirmation of the 4th executable fingerprint and working directory, `re2dj --run ez2dj4th` integration, and a write overlay remain separate tasks.
